1.1 첫 번째 질문¶

기존 데이터 플랫폼과 Palantir Foundry는 무엇이 다른가?

  • 기존 데이터 플랫폼은 데이터를 수집·저장·정제·분석하는 데 강하다.
  • Foundry는 데이터에 업무 의미를 부여하고, 누가 무엇을 판단하고 어떤 행동을 할 수 있는지까지 연결한다.
  • 즉, Foundry의 차별점은 단순한 데이터 처리량이 아니라 분석 결과를 운영 행동으로 연결하는 구조에 있다.

2. 기존 데이터 플랫폼과 Foundry의 차이¶

2.1 기존 데이터 플랫폼의 전형적인 구조¶

일반적인 데이터 플랫폼은 다음 요소로 구성된다.

  • ERP, MES, CRM, WMS, 센서, Excel, 외부 API 등 원천 시스템
  • 데이터 웨어하우스 또는 데이터 레이크
  • ETL·ELT 파이프라인
  • 분석용 데이터 마트
  • BI 대시보드
  • 통계·머신러닝 분석 환경

이 구조는 매우 중요하며 Foundry도 이러한 기반 기능을 포함하거나 연결한다. 따라서 “기존 플랫폼은 낡고 Foundry만 옳다”는 식으로 이해하면 안 된다.

기존 플랫폼의 일반적인 흐름은 다음과 같다.

flowchart TD A[ERP·MES·센서·파일] --> B[데이터 레이크/웨어하우스] B --> C[정제·통합] C --> D[데이터 마트] D --> E[BI·분석] E --> F[보고서·회의] F --> G[현업이 별도 시스템에서 조치]

분석 결과가 현업 실행으로 이어지려면 보통 다음 과정이 추가된다.

  1. 분석가가 이상을 발견한다.
  2. 보고서를 작성한다.
  3. 회의를 진행한다.
  4. 책임자를 정한다.
  5. ERP나 MES에 다시 접속한다.
  6. 담당자가 주문·작업·재고·품질 상태를 수정한다.
  7. 결과를 별도 문서로 기록한다.

이때 데이터 분석과 업무 실행 사이에 시간이 지연되고, 책임과 근거가 여러 시스템에 분산될 수 있다.

2.2 Foundry의 관점¶

Foundry는 데이터 처리만이 아니라 다음을 연결하려는 플랫폼이다.

  • 현실의 업무 대상
  • 대상의 현재 상태
  • 대상 간 관계
  • 조직의 판단 기준
  • 실행 가능한 액션
  • 액션의 권한과 책임
  • 상태 변경 이력
  • 후속 영향과 결과
flowchart TD A[원천 데이터] --> B[정제된 데이터] B --> C[Ontology: 객체·관계·상태] C --> D[분석·모델·규칙] D --> E[운영 앱] E --> F[승인·액션] F --> G[객체 상태 변경] G --> H[영향 범위 추적] H --> C

2.4 중요한 보정¶

전문적으로는 다음처럼 이해해야 한다.

  • 데이터 레이크도 충분히 잘 설계하면 카탈로그, 품질, 계보, 권한을 갖출 수 있다.
  • 기존 ERP도 워크플로와 승인 기능을 가질 수 있다.
  • Foundry의 장점은 개별 기능 하나가 아니라, 데이터·모델·업무 객체·애플리케이션·액션·보안·감사를 같은 의미 체계로 연결하는 접근에 있다.
  • 온톨로지는 데이터 레이크를 없애는 것이 아니라, 데이터 레이크 위에 업무 의미와 실행 계층을 더한다.

3. 데이터 레이크와 온톨로지 비교¶

3.1 데이터 레이크란 무엇인가¶

데이터 레이크는 형식이 다른 대규모 데이터를 원형 또는 준원형 상태로 저장하는 기반이다.

저장할 수 있는 예:

  • 관계형 데이터베이스 추출 데이터
  • CSV·Excel
  • 로그
  • PDF·이미지
  • 설비 센서 시계열
  • 품질검사 이미지
  • 이메일·문서
  • 외부 시장 데이터

장점¶

  • 대량 데이터 수집
  • 다양한 형식 수용
  • 원천 보존
  • 분석 목적에 따른 재가공
  • 머신러닝 학습 데이터 확보
  • 장기 이력 저장

위험¶

  • 메타데이터와 책임자가 없으면 데이터 늪이 될 수 있음
  • 동일한 고객·제품·설비가 여러 코드로 중복될 수 있음
  • 데이터의 의미를 현업이 이해하기 어려울 수 있음
  • 분석 결과가 실제 업무 행동으로 연결되지 않을 수 있음

3.2 온톨로지란 무엇인가¶

Foundry 관점의 온톨로지는 조직이 다루는 현실을 다음 요소로 표현하는 운영 의미 계층이다.

  • 객체 유형(Object Type)
  • 객체 인스턴스(Object)
  • 속성(Property)
  • 링크(Link)
  • 액션(Action)
  • 함수와 모델(Function/Model)
  • 권한(Authorization)
  • 상태와 전이(State/Transition)
  • 업무 앱(Object View/Workshop)

3.3 비유¶

개념 비유
데이터 레이크 모든 원재료와 기록을 모아 둔 대형 창고
데이터 카탈로그 창고 위치와 품목을 알려주는 목록

5. Data Connection¶

5.1 정의¶

Data Connection은 외부 시스템이나 다른 Foundry 환경의 데이터를 Foundry로 동기화하기 위한 연결 계층이다.

5.2 연결 대상¶

  • Odoo ERP
  • MES
  • WMS
  • PostgreSQL·Oracle·SQL Server
  • 파일 저장소
  • 클라우드 스토리지
  • API
  • 제조 설비 게이트웨이
  • IoT 플랫폼
  • 다른 Foundry 인스턴스

5.3 핵심 개념¶

  • Source: 외부 시스템에 대한 하나의 연결
  • Sync: 원천 데이터를 Foundry 데이터셋으로 가져오는 작업
  • Batch Sync: 일정 또는 수동 실행으로 묶음 데이터를 동기화
  • Incremental Sync: 변경분만 가져오는 동기화
  • Credential: 접속 자격증명
  • Schema: 가져오는 필드와 데이터 형식
  • Freshness: 데이터가 얼마나 최신인지 나타내는 상태

5.4 색종이 공장 연결 설계¶

원천 데이터 주기 사용 목적
Odoo 제품·BOM·MO·WO·재고·Lot 5~15분 생산·재고·추적
설비 PLC/MQTT 속도·온도·압력·정지 초~분 이상 탐지
품질검사 장비 색차·치수·인쇄 결함 실시간/배치 품질 판정
Excel 작업조·임시 계획 일 1회 보조 마스터
고객 클레임 유형·사진·주문번호 사건 발생 시 품질 Case
회계 표준원가·실제원가 일·월 원가 분석

5.5 설계 원칙¶

  1. 원천 시스템의 책임자를 명확히 한다.
  2. 원천 데이터는 가급적 원형에 가깝게 보존한다.
  3. 수정은 원천에서 해야 하는지 Foundry Action에서 해야 하는지 결정한다.
  4. 동기화 실패가 어떤 앱에 영향을 주는지 계보를 관리한다.
  5. 개인정보·영업비밀·생산비밀에 대한 접근권한을 분리한다.

6. Contour¶

6.1 정의¶

Contour는 데이터셋을 포인트앤클릭 방식으로 탐색하고 변환·집계·시각화하는 분석 도구이다.

6.2 적합한 질문¶

  • 데이터에 결측치가 얼마나 있는가?
  • 설비별 불량률은?
  • 색상별 생산량은?
  • 특정 기간에 생산시간이 증가했는가?
  • 작업조별 품질 차이가 있는가?
  • 어떤 원재료 Lot에서 이상이 집중되는가?

6.3 색종이 예제¶

분석 대상:

text

제품 코드
색상
인쇄기
작업조
원재료 Lot
계획 수량
양품 수량
불량 수량
작업 시간
정지 시간

파생 지표:

text

시간당 생산량 = 양품 수량 / 실제 작업 시간
설비 가동률 = 가동 시간 / 계획 시간

6.4 Contour의 한계¶

Contour에서 좋은 분석을 만들었다고 해서 자동으로 업무 조치가 발생하는 것은 아니다.
다음 단계가 필요하다.

  • 분석 결과를 온톨로지 객체 속성으로 제공
  • 위험 상태 규칙 정의
  • 책임자와 가능한 액션 정의
  • Workshop 화면에서 조치
  • Action을 통해 객체 또는 외부 시스템 변경

7. Pipeline Builder¶

7.1 정의¶

Pipeline Builder는 원천 데이터셋을 시각적으로 정제·결합·변환하여 재사용 가능한 데이터 파이프라인을 만드는 도구이다.

7.2 전형적인 흐름¶

flowchart LR A[Odoo MO] --> J[키 정규화] B[Odoo WO] --> J C[재고 이동] --> J D[Lot] --> J E[품질검사] --> J F[설비센서] --> J J --> T[정제·결합] T --> M[생산실적 데이터셋] T --> Q[품질추적 데이터셋] T --> O[Ontology 객체 원천]

7.3 주요 작업¶

  • 불필요한 칼럼 제거
  • 데이터 형식 변환
  • 제품코드·설비코드 표준화
  • 중복 제거
  • MO와 WO 연결
  • 투입 Lot와 산출 Lot 연결
  • 센서 데이터를 작업시간 구간에 맞게 결합
  • 파생 지표 계산
  • 오류 행 격리
  • 증분 처리

8.6 온톨로지 설계 원칙¶

  1. 테이블을 그대로 객체로 복사하지 않는다.
  2. 현업이 실제로 말하는 명사를 객체로 선택한다.
  3. 의사결정에 필요한 상태를 우선 정의한다.
  4. 링크는 단순 조회뿐 아니라 영향 범위를 설명해야 한다.
  5. 액션은 권한·조건·결과를 함께 설계한다.
  6. 객체의 원천 시스템과 책임 부서를 명시한다.
  7. 과도하게 거대한 객체 하나에 모든 속성을 넣지 않는다.
  8. 변경 이력과 감사 요구를 설계 초기에 반영한다.

9. Object Explorer¶

9.1 정의¶

Object Explorer는 온톨로지의 객체를 검색하고, 필터링하며, 관계를 따라가고, 객체 집합을 비교하는 도구이다.

  • 제품명
  • 생산일
  • 제조오더
  • 작업오더
  • 설비
  • 작업자
  • 원재료 Lot
  • 검사 결과
  • 현재 재고
  • 출하된 고객
  • 관련 품질사고
  • 가능한 액션

Functions는 온톨로지 객체와 데이터를 이용해 계산, 검증, 추천, 규칙, 복잡한 비즈니스 로직을 구현하는 기능이다.

11.1 정의¶

Workshop은 온톨로지, Functions, Actions를 조합하여 현업 사용자가 쓰는 운영 애플리케이션을 만드는 도구이다.

13. Apollo¶

13.1 정의¶

Apollo는 소프트웨어를 여러 환경에 배포하고 업그레이드하며 운영 상태를 관리하기 위한 Palantir의 지속적 배포·운영 플랫폼이다.

13.2 Foundry 업무 기능과의 구분¶

  • Foundry: 데이터·분석·온톨로지·운영 애플리케이션
  • Apollo: 소프트웨어 제품의 배포·업그레이드·운영 관리

13.3 제조기업 적용¶

한국 본사, 국내 공장, 베트남 법인, 폐쇄망 공장에 서로 다른 배포 제약이 있을 수 있다.

Apollo 관점에서 고려할 사항:

  • 환경별 릴리스 승인
  • 폐쇄망·제한망 배포
  • 버전 일관성
  • 점진적 업데이트
  • 장애 시 롤백
  • 운영 상태 확인
  • 보안 취약점 대응

Apollo는 생산오더를 관리하는 ERP 기능이 아니다.
Foundry 위에 만들어진 앱과 서비스, 또는 별도 소프트웨어 제품을 안정적으로 배포·운영하는 계층이다.

15. 온톨로지의 핵심 구조¶

15.1 객체(Object)¶

객체는 현실의 대상이다.

예:

  • 사람
  • 제품
  • 설비
  • 주문
  • 작업오더
  • Lot
  • 품질사고

객체의 핵심은 단순히 속성값을 가진다는 것이 아니라, 현재 상태와 업무 맥락을 가진다는 점이다.

15.2 액션(Action)¶

액션은 객체에 대해 실행할 수 있는 업무 행동이다.

예:

  • 제조오더 승인
  • 작업 시작
  • 작업 중지
  • 출하 보류
  • 재작업 지시

액션은 다음을 포함한다.

  • 실행 주체
  • 실행 조건
  • 입력값
  • 변경 대상
  • 상태 변화
  • 후속 효과
  • 감사 기록

15.3 링크(Link)¶

링크는 객체 간 관계이다.

예:

  • 제조오더가 작업오더를 포함한다.
  • 작업오더가 설비에서 수행된다.
  • 작업오더가 원재료 Lot를 소비한다.
  • 완제품 Lot가 고객에게 출하된다.

링크는 영향 범위를 정의한다.

16. 판단 중심 온톨로지의 5가지 원리¶

16.1 스스로 질문에 답하는 구조¶

데이터 구조 안에서 다음이 드러나야 한다.

  • 상황이 정상인지
  • 누가 판단해야 하는지
  • 어떤 행동이 가능한지
  • 행동 결과가 무엇인지
  • 어디까지 영향이 미치는지

예¶

단순 값:

text
인쇄기 온도 = 87℃

판단 구조:

text
객체: 인쇄기 2호
현재 온도: 87℃
정상 범위: 60~80℃
상태: 위험
책임 역할: 생산관리자
가능 액션: 작업중지, 정비요청, 작업재배정
관련 작업오더: WO-260802-17
영향 제조오더: MO-260802-01

16.2 값이 아닌 상태 중심¶

값은 관측치이고, 상태는 조직의 판단이다.

text
색차 ΔE = 2.8

이 값만으로는 행동을 결정하기 어렵다.

상태 규칙:

ΔE 상태 기본 조치
0.0~1.0 정상 계속 생산
1.0 초과~2.0 주의 표본 확대
2.0 초과~3.0 위험 품질승인 필요
3.0 초과 중단 생산중지·원인조사

실제 기준은 제품·고객·계약 사양에 따라 설정해야 한다.

16.3 비교가 아닌 상태 전이를 기록¶

단순 비교:

text
어제 불량률 1.8%
오늘 불량률 4.6%

상태 전이:

text
09:10 정상
10:25 주의
11:05 위험
11:12 작업중지
11:20 품질 Case 생성
13:40 설비 청소 완료
14:10 시험생산
14:45 정상 복귀

상태 전이 기록은 다음 질문에 답한다.

  • 언제 문제가 시작되었는가?
  • 어떤 데이터가 원인이었는가?
  • 누가 상태를 바꾸었는가?
  • 어떤 조치가 효과가 있었는가?
  • 재발을 방지했는가?

16.4 액션 가능성을 포함¶

각 상태에서 허용되는 액션을 구조화한다.

작업오더 상태 허용 액션
대기 작업자 배정, 설비 배정, 일정 변경

품질 보류 재검사, 재작업, 폐기 승인
완료 실적 확정, 원가 마감

“할 수 있는가, 없는가”가 데이터 구조와 권한에 의해 통제된다.

python
from dataclasses import dataclass
from enum import Enum


class QualityStatus(str, Enum):
    NORMAL = "정상"
    CAUTION = "주의"
    RISK = "위험"
    STOP = "중단 필요"


@dataclass(frozen=True)
class ColorQualityRule:
    caution_threshold: float = 1.0
    risk_threshold: float = 2.0
    stop_threshold: float = 3.0


def classify_delta_e(
    delta_e: float,
    rule: ColorQualityRule = ColorQualityRule(),
) -> QualityStatus:
    if delta_e < 0:
        raise ValueError("delta_e는 0 이상이어야 합니다.")

    if delta_e <= rule.caution_threshold:
        return QualityStatus.NORMAL
    if delta_e <= rule.risk_threshold:
        return QualityStatus.CAUTION
    if delta_e <= rule.stop_threshold:
        return QualityStatus.RISK
    return QualityStatus.STOP

26.4 Python: Odoo JSON-2 API 호출 구조 예¶

아래 코드는 구조를 설명하기 위한 예시이며, 실제 URL·헤더·모델·권한은 조직 환경에서 확인해야 한다. Odoo 외부 API는 요금제와 배포 방식에 따라 사용 가능 범위가 다를 수 있다.

python
from __future__ import annotations

import os
from typing import Any

import requests


class OdooApiError(RuntimeError):
    pass


class OdooJson2Client:
    def __init__(self, base_url: str, api_key: str, timeout: int = 30) -> None:
        self.base_url = base_url.rstrip("/")
        self.api_key = api_key
        self.timeout = timeout

    def call(
        self,
        model: str,
        method: str,
        payload: dict[str, Any],
    ) -> dict[str, Any]:
        url = f"{self.base_url}/json/2/{model}/{method}"
        headers = {
            "Authorization": f"bearer {self.api_key}",
            "Content-Type": "application/json",
        }

        response = requests.post(
            url,
            json=payload,
            headers=headers,
            timeout=self.timeout,
        )

        if not response.ok:
            raise OdooApiError(
                f"Odoo API 오류: status={response.status_code}, "
                f"body={response.text[:500]}"
            )

        return response.json()


def hold_manufacturing_order(
    client: OdooJson2Client,
    manufacturing_order_id: int,
    reason: str,
) -> dict[str, Any]:
    # 실제 구현에서는 사용자 정의 서버 메서드 또는
    # 검증된 업무 액션을 호출하는 방식이 바람직하다.
    return client.call(
        model="mrp.production",
        method="write",
        payload={
            "ids": [manufacturing_order_id],
            "vals": {
                "x_foundry_hold": True,
                "x_foundry_hold_reason": reason,
            },
        },
    )


if __name__ == "__main__":
    client = OdooJson2Client(
        base_url=os.environ["ODOO_BASE_URL"],
        api_key=os.environ["ODOO_API_KEY"],
    )

맺음말¶

기존 데이터 플랫폼은 데이터를 모으고 분석할 수 있게 만든다.
Foundry Ontology는 여기에 한 걸음 더 나아가 다음을 묻는다.

이 데이터가 현실의 어떤 대상을 의미하는가?
그 대상은 지금 어떤 상태인가?
누가 어떤 근거로 판단해야 하는가?
지금 실행 가능한 행동은 무엇인가?
행동하면 어떤 대상에 영향이 미치는가?
그 결정과 결과를 어떻게 추적할 것인가?

색종이 제조공장에서 이러한 질문은 다음과 같이 구체화된다.

text
어떤 원재료 Lot가
어떤 작업오더와 설비를 거쳐
어떤 색상 반제품 Lot가 되었고,
어떤 추림 작업에서
어떤 완제품 Lot에 포함되어
어느 고객에게 출하되었는가?

품질 문제가 발생했을 때
누가 출하를 보류할 수 있고,
어떤 근거로 결정했으며,
어떤 재작업과 검증을 거쳐
다시 정상 상태로 돌아왔는가?

이 질문에 데이터 구조 자체가 답하고, 사용자가 그 자리에서 책임 있는 행동을 할 수 있게 만드는 것이 판단 중심 온톨로지의 핵심이다.
